# Правила разработки

Проектные конвенции для агентов и разработчиков (общие с modamakers_site).
Контекст проекта — бриф «Бесплатный сайт по дзюдо» в ClickUp и `README.md`.

## 1. Версии пакетов

Устанавливай последнюю совместимую версию пакета (`pnpm add pkg@latest`,
либо сверяйся с `npm view pkg version` перед установкой), а не первую
попавшуюся из памяти.

Исключение — когда последняя версия ломает peer-зависимость. Пример в этом
проекте: `typescript` зафиксирован на `^6.0.3`, а не на мажорной `7.x`,
потому что `typescript-eslint` требует `typescript: >=4.8.4 <6.1.0`. Если
встречаешь такой конфликт — фиксируй совместимую версию и оставляй комментарий
в `package.json`/коммите, почему именно эта версия.

## 2. Lint/typecheck — только при изменении `.ts`/`.tsx`

Перед `pnpm run lint && pnpm run typecheck` проверь `git diff --name-only`
(или `--staged`). Если среди изменённых файлов нет `.ts`/`.tsx` (например,
правка только `.md`/`.csv`/`.json`-конфига без кода) — пропускай эти шаги
локально, не трать время. CI всё равно прогоняет их на каждый PR как
подстраховку — это не отменяется.

## 3. Next.js colocation

Файлы, нужные только одной странице (компоненты, хуки, утилиты, типизированный
контент), живут рядом с этой страницей — не в общих `src/components/`,
`src/lib/`, `src/hooks/`.

Переиспользуемые между несколькими маршрутами файлы — в `src/components/`,
`src/lib/`, `src/hooks/` и т.д.

Паттерн колокации в App Router: подпапка с префиксом `_` рядом с `page.tsx`
(Next.js гарантированно не трактует её как маршрут). Пример из этого
проекта — компоненты карточки техники нужны только ей:

```
src/app/techniques/[slug]/
  page.tsx
  _components/
    facts.tsx
    steps.tsx
    video.tsx
```

Если компонент из `_components/` понадобится на другой странице —
тогда (и только тогда) поднимай его в `src/components/`.

## 4. Никаких `React.*`-типов через namespace

Импортируй типы напрямую:

```ts
import type { ReactNode, FC, MouseEvent } from 'react';
```

Не пиши `React.ReactNode`, `React.FC`, `React.MouseEvent` и т.п. Правило
закреплено в `eslint.config.mjs` (`no-restricted-syntax` на
`TSQualifiedName[left.name='React']`) — лишние обращения через `React.`
будут падать на `pnpm run lint`.

## 5. Один TSX-компонент на файл

Если нужен новый компонент — новый файл. Хелперы, типы и константы могут жить
в одном файле с единственным компонентом (см. `video.tsx`:
`Video` + хелпер `youtubeId`).

## 6. Лимит 300 строк на компонент

Компонент длиннее 300 строк — сигнал разбить на более мелкие, если это
реально возможно (вынести подблоки в отдельные компоненты, как сделано с
`QuizSetup`/`QuizQuestion`/`QuizResult` для страницы тестов).

Компонент большего размера допустим, только если есть реальная причина
(например, сложная форма с валидацией, которую нет смысла дробить). В этом
случае — комментарий в начале файла, почему разбиение не применено.

Enforced как `warn` в ESLint (`max-lines` для `**/*.tsx`, 300 строк без
пустых строк/комментариев) — предупреждение, не ошибка, т.к. решение
"есть ли реальная причина" требует человеческого суждения.


## 7. Пиши чистый, удобочитаемый код, соответствующий принципам SOLID и DRY.
## 8. Предпочитай функциональные компоненты и декларативный подход.
## 9. По умолчанию все компоненты — Server Components.
## 10. Используй директиву "use client" только тогда, когда это необходимо (хуки useState/useEffect, обработчики событий вроде onClick, использование браузерных API).
## 11. Держи клиентские компоненты как можно ниже по дереву компонентов.
## 12. Запрашивай данные на сервере (в Server Components) с помощью асинхронных функций (async/await) напрямую из БД или через fetch.
## 13. Используй встроенное кэширование Next.js. Настраивай ревалидацию через revalidatePath или revalidateTag.
## 14. Для отправки форм и изменения данных используй Server Actions ("use server").
## 15. Обрабатывай состояния загрузки на клиенте с помощью хука useTransition.
## 16. Для локального UI-стейта используй useState.
## 17. Для передачи данных по дереву — React Context (помни, что провайдер должен быть Client-компонентом).
## 18. Для условного объединения классов Tailwind используй функцию cn() (комбинация clsx и tailwind-merge).
## 19. Для ссылок внутри приложения используй <Link /> из next/link для автоматического префетчинга страниц.
## 20. Используй файлы loading.tsx для SSR-стриминга (Streaming) и error.tsx для перехвата ошибок на уровне маршрутов.
## 21. Избегай ненужных useEffect. По возможности выноси логику в Server Components или вычисляй стейт «на лету» во время рендеринга.
## 22. Экспортируй компоненты как именованные функции: export function MyComponent() {} вместо export default. (Исключение — файлы страниц Next.js, где export default обязателен).
## 23. Разделяй E2E-тесты (тестирование полных пользовательских сценариев на страницах) и Component Tests (изолированное тестирование UI-компонентов в браузере).
## 24. Храни E2E-тесты в папке tests/e2e/, а компонентные тесты рядом с самими компонентами с расширением .spec.tsx.
## 25. Используй паттерн Page Object Model (POM) для сложных страниц, чтобы изолировать локаторы и действия от самого текста теста.
## 26. Всегда используй современные локаторы Playwright: предпочтительно page.getByRole(), page.getByText(), page.getByLabel() для поддержки доступности (accessibility). Избегай жестких CSS-селекторов (.btn-submit).
## 27. Для перехода по страницам Next.js используй page.goto('/route') и проверяй успешную гидратацию и загрузку данных перед действиями.
## 28. Перехватывай и мокай API-запросы с помощью page.route(), чтобы тесты не зависели от стабильности реального бэкенда.
## 29. Изолируй Server Actions в тестах, мокая сетевые ответы, которые они вызывают, если это необходимо.
## 30. Никогда не используй хардкодные задержки времени (page.waitForTimeout()). Вместо этого дожидайся появления элементов, изменения текста или завершения сетевых запросов (page.waitForResponse()).
## 31. Используй веб-ферст утверждения (Web-First Assertions), такие как await expect(locator).toBeVisible(), так как они содержат встроенные автоматические повторные попытки (auto-retry).

## 32. `data-testid` в нотации БЭМ — по завершении разработки страницы

По завершении разработки страницы покрой её функциональность тестами
(правила 23–31). Для локаторов, которые не должны зависеть от видимого
текста (когда появятся другие языки, текст кнопки будет меняться по локали),
добавляй `data-testid` в нотации БЭМ: `блок__элемент` (`cookie-banner__accept`,
`locale-switcher__option`, `home-steps-overview__card`). Для локаторов, где
текст стабилен и значим (заголовки, вообще — где подходит правило 26),
предпочитай `getByRole`/`getByText`/`getByLabel` — `data-testid` не замена
семантическим локаторам, а дополнение для языконезависимых случаев.

Не добавляй `data-testid` заранее «на будущее» — только когда пишешь тест,
которому он нужен (иначе накопится разметка, которую никто не использует).

## 33. Статический экспорт

Сайт собирается в статический HTML (`output: 'export'` в `next.config.ts`, деплой — Cloudflare
Pages или Netlify). Поэтому нет Server Actions, API-маршрутов, middleware, `revalidatePath`
и оптимизации картинок на сервере. Правила 12–14 и 28–29 применимы только в части, которая
работает без сервера: данные читаются при сборке из `data/judo-dataset.json`
(`src/lib/dataset`), пользовательское состояние (история тестов, чек-листы) — в localStorage.
У каждого динамического маршрута — `generateStaticParams` и `dynamicParams = false`.

`compiler.reactRemoveProperties` вырезает `data-testid` из прод-сборки; в `next dev` (и в
`pnpm run test:e2e`) атрибуты остаются.

## 34. Контент

Тексты, вопросы и картинки сайта-референса не копируем — пишем свои. Названия техник и
классификация — общедоступная номенклатура Кодокана. Тексты требуют вычитки тренером.
